# Security case: authentication and encryption between the game window and the game server

This document argues that the design in [`authentication.md`](authentication.md) (version 2) protects Warped's
network traffic well enough for its purpose: games among friends, over the internet, on servers the friends run.
It is written so that a person, or a security expert they hire, can review the design claim by claim, and so that
implementers know what evidence each claim needs.

- **Status:** design only. v2 is built in step C1 of [`game/REFACTOR_PLAN.md`](../../game/REFACTOR_PLAN.md); the
  evidence column below says which tests will back each claim, and none exists yet. The demo still runs v1
  (section 8).
- **Owner:** whoever changes `authentication.md` updates this document in the same PR.
- **Reviewed by:** nobody yet. A review adds a line here: who, when, what they checked, what they found.

## 1. Scope

**In scope:** the UDP traffic between the game window (`warped`) and the game server (`warped-server`): the
handshake, the encryption and authentication of each datagram, the game password (how it is made, kept, typed and
used), and the server's behaviour towards datagrams from anyone on the internet.

**Out of scope**, each owned elsewhere or deliberately left out:

- Cheating by players who have the password (the server takes each window's word for its hits; the game design
  treats players as friends).
- The security of the machines: the players' Macs, the server's VM, and the cloud account (`infra/`, the infra
  stack).
- How the Mac app is signed, notarized and downloaded (the infra stack).
- Large-scale denial of service (floods that fill the server's network link); section 7 says what the design does
  and doesn't do.
- The local-network discovery beacon's privacy (it announces a port, nothing secret).

## 2. The system

```text
 Player's Mac                                       Server (a cloud VM, or a Mac)
 +----------------------------+     internet       +------------------------------+
 | warped (game window)       |  UDP datagrams     | warped-server (one game)     |
 |  password file (0600) -----+--------------------+--- password file (0600)      |
 |  session keys (memory)     |  handshake, then   |   session keys per player    |
 |                            |  encrypted game    |   (memory)                   |
 +----------------------------+  messages          +------------------------------+
        ^                                                    ^
        | the password, sent once by the owner over a private channel (e.g. WhatsApp)
        +----------------------------------------------------+
```

- **Trust boundary:** the network between a window and the server, and every other host on the internet.
- **The secret:** one game password per server, generated by `warped-server create-game-password` (160 random
  bits), shared by the server's owner with every player.
- **The handshake:** Noise `NNpsk0` with X25519, ChaCha20-Poly1305 and SHA-256, through the `snow` library. It
  proves on both sides that the other knows the password, and makes fresh keys per session.
- **The datagrams:** after the handshake, every game message is a `Transport` datagram: a session index, a counter
  used as the nonce, and the message sealed with ChaCha20-Poly1305. A 64-datagram window rejects replays.
- **Byte layouts and sizes:** `authentication.md`.

## 3. What is protected

| Asset | Why it matters |
| --- | --- |
| Who can play in a game | the core promise: only friends with the password |
| The integrity of game messages | a stranger mustn't move, shoot as, or eliminate a player, or end a game |
| The confidentiality of game messages | players' positions, scores and choices are nobody else's business (low stakes, but cheap to protect) |
| The game password | leaking it opens the game to whoever gets it |
| The server's availability | a game is ruined if strangers can knock it over cheaply |
| Third parties' networks | the server mustn't be usable to flood someone else (reflection and amplification) |

## 4. Assumptions

Each claim in section 6 depends on some of these. A reviewer should challenge them first.

- **A1. Private delivery:** the owner gives the password only to the players, over a channel strangers can't read
  (an end-to-end encrypted messenger).
- **A2. Trusted endpoints:** the players' Macs and the server's machine aren't compromised; their operating
  systems' random number generators are sound.
- **A3. Trusted players, for the network:** a player with the password doesn't attack other players' connections.
  (Anyone with the password can, see L2.)
- **A4. Sound cryptography:** X25519, ChaCha20-Poly1305, SHA-256 and HKDF are secure as standardized, and the
  Noise framework's `NNpsk0` pattern gives the properties the Noise specification states for it.
- **A5. A correct implementation:** `snow` implements Noise correctly (it has had no formal audit, see L1), and
  Warped's code around it follows `authentication.md` (checked by the tests in section 6 and the checklist in
  section 10).
- **A6. The network attacker:** may be anywhere on the internet, may forge source addresses, and, on some paths
  (shared Wi-Fi, an ISP), may read, record, drop, delay, reorder, replay and inject datagrams (the Dolev-Yao model).

## 5. Adversaries

| Id | Who | Can | Doesn't have |
| --- | --- | --- | --- |
| S1 | a stranger off the path (a scanner, someone who learned the server's address) | send any datagram, with any source address | the password, the traffic |
| S2 | a passive observer on the path (same café Wi-Fi) | read and record all traffic | the password |
| S3 | an active attacker on the path | S2, plus change, drop, replay and inject datagrams | the password |
| S4 | a former player, after the password was changed | an old password, recordings of old games | the current password |
| S5 | a current player | the current password | another player's session keys |
| S6 | a flooder | send many datagrams from many addresses | the password |

## 6. Claims, arguments and evidence

Evidence marked *planned* is a test of step C1 (`authentication.md`, "Tests every implementation keeps") or of the
plan's section 7; it must exist and pass before v2 ships.

### C1. Only holders of the password can open a session (against S1, S3, S6)

- **Argument:** in `NNpsk0` the password-derived key (psk) is mixed into the handshake before the first message,
  and that message's payload is encrypted and authenticated with keys that depend on it. Without the psk, a
  `HandshakeInit` doesn't verify and the server drops it before any key exchange or state. A
  `HandshakeResponse` likewise only verifies for someone with the psk, so the window also knows it reached a server
  with the password.
- **Evidence (planned):** handshake tests (right password opens a session; wrong password gets no reply and leaves
  no state); the simulated-network "strangers" scenario (plan 7.5, scenario 7); a fuzz test of the server's datagram
  handling.

### C2. Strangers can't read game traffic (against S2, S3)

- **Argument:** every game message after the handshake is encrypted with ChaCha20-Poly1305 under keys derived from
  an ephemeral X25519 exchange and the psk; an attacker without the psk can't derive them.
- **Evidence (planned):** a test that no game message's bytes appear in the clear in any datagram; review of the
  code path that every message takes (section 10).

### C3. Strangers can't change, inject or replay game messages (against S3)

- **Argument:** ChaCha20-Poly1305 authenticates each datagram; changing any byte, including the header (which
  selects the session and the nonce), makes it fail. Each direction numbers its datagrams; the receiver rejects a
  counter it has seen or one more than 64 behind its highest (RFC 6479-style window, as in WireGuard and IPsec).
- **Evidence (planned):** transport tests: one flipped bit anywhere is dropped; a replayed counter is dropped;
  reordering within 64 is accepted once each; older is dropped.

### C4. Recorded games stay private if the password leaks later (against S4)

- **Argument:** each session's keys come from fresh ephemeral X25519 keys, deleted when the session ends, mixed
  with the psk. Knowing the psk afterwards doesn't reveal the ephemeral secrets, so recordings can't be decrypted
  (forward secrecy).
- **Limit:** a password holder who is on the path during a game can impersonate the server to a player (L2). Forward
  secrecy protects the past, not a live game against S5.
- **Evidence:** the Noise specification's security properties for `NN` with ephemeral-ephemeral DH (reference 1),
  for reviewers to confirm for `NNpsk0`.

### C5. The password can't be guessed, online or offline (against S1, S2, S3)

- **Argument:** passwords are generated with 160 bits from the OS's random generator and never chosen by people.
  A recorded handshake lets an attacker test guesses offline, but 2^160 guesses is out of reach. Online guessing is
  slower still: wrong guesses get no reply, and handshakes are rate-limited per IP.
- **Evidence (planned):** password tests (generation uses the OS generator; parsing refuses wrong length, checksum
  and alphabet); the server refuses a missing, empty or malformed password at start (C7).

### C6. The server can't be used to flood a third party (against S1, S6)

- **Argument:**
  - the only reply to an unproven address is a `HandshakeResponse` (59 bytes) to a `HandshakeInit` padded to 71
    bytes, or a 4-byte `OtherVersion`;
  - every other datagram from an unproven address gets nothing;
  - large messages (the `Welcome`, snapshots) only go to a session whose window has proven it receives at its
    address, by sending a valid `Transport` datagram made with keys from the response.
- **Evidence (planned):** the amplification test (no reply to an unproven address is longer than its cause);
  handshake rate-limit tests.

### C7. A server never runs without a password (against S1)

- **Argument:** `warped-server` refuses to start, with exit code 2, without `--game-password-file`, or when the
  file is empty or not a valid `warped2-` password. There is no flag to turn this off.
- **Evidence (planned):** server start tests for each case.

### C8. A player's session can't be taken over by changing address (against S1, S3)

- **Argument:** the server moves a session to a new address only on a datagram that authenticates under that
  session's keys with a counter not seen before. An attacker without the keys can't make one, and a replayed one is
  rejected by C3's window. An on-path attacker who re-sends a fresh datagram from another address can redirect the
  server's replies, but can't read them (C2); that is a denial of service, which an on-path attacker has anyway.
- **Evidence (planned):** the roaming test (a valid datagram from a new address moves the session; a replayed one
  doesn't).

### C9. The password doesn't leak from the machines through the game (against S2, S5's onlookers)

- **Argument:**
  - password files are created with mode 0600;
  - the password is read from a file, never from the command line (where other users' `ps` would show it), and
    never logged, printed or drawn on screen;
  - `create-game-password` prints the file's path, not the password.
- **Evidence (planned):** a test that `create-game-password` writes mode 0600 and prints no password; review
  (section 10).

## 7. Known limitations and residual risks

| Id | Limitation | Consequence | Why accepted, and what would remove it |
| --- | --- | --- | --- |
| L1 | `snow` has had no formal audit (its README says so) | a bug in its handshake state machine could break C1 to C4 | it is the most used Rust Noise implementation, tested against Noise's vectors and fuzzed, and its ciphers come from widely used crates; the user accepted it on 2026-11-08. An audit of `snow`, or a switch to an audited implementation, would remove it |
| L2 | one password shared by everyone in a game | any player can impersonate the server to other players, or read their traffic if on their path; players can't be told apart cryptographically | the game is among friends (A3). Per-player keys (e.g. Noise `IK` with each player's public key) would remove it, at the cost of key distribution |
| L3 | no revocation but changing the password | a removed friend keeps access until the owner makes a new password and shares it with everyone else | small groups; rotation is one command and a restart |
| L4 | traffic analysis | an observer sees that a game is on, its datagram sizes and timing, and players' IP addresses | inherent to UDP games; padding and timing noise would cost bandwidth for little gain |
| L5 | `OtherVersion` is unauthenticated | a forged one can show a player "the server runs another version" | it carries no secret and changes no state; it exists so real version mismatches are explained |
| L6 | floods | a big enough flood still fills the link; each `HandshakeInit` costs the server one hash-and-verify | per-IP limits and dropping without replies keep the cost per datagram small; large-scale floods need the cloud provider's protection |
| L7 | passwords are kept in plain files (0600), not the macOS Keychain | malware running as the player can read them | A2; moving the app's copy to the Keychain is a later improvement (infra stack) |
| L8 | no protection against cheating by players | out of scope (section 1) | an authoritative server would be needed (plan, phase C notes) |
| L9 | supply chain | a compromised crate update could break everything | versions pinned in `Cargo.lock`, only releases at least 7 days old (root `AGENTS.md`); review dependency updates |
| L10 | the demo still runs v1 until it is retired (section 8) | demo games aren't encrypted and may run without a password | the demo is kept only as a reference; play happens in `game/` once step C1 lands |

## 8. The demo's v1 in the meantime

The demo (and `game/` before step C1) uses the infra stack's v1 (#181, `authentication.md`, "v1"):

- an HMAC-SHA256 proof of an address-keyed cookie;
- a 64-bit token on later messages;
- no encryption;
- an optional, person-chosen password.

Against S1 it keeps strangers out when a password is set. Against S2 and S3 it offers no confidentiality, and the
token, being sent in the clear, could be reused by an on-path attacker from the player's address. A chosen password
can be guessed offline from a recorded join. From step A5 on, `warped-server` in `game/` already refuses to start
without a password. Don't rely on v1 for games over untrusted networks.

## 9. Questions for reviewers

1. Does `Noise_NNpsk0_25519_ChaChaPoly_SHA256` give the properties C1 to C4 claim? Is `psk0` the right
   placement, or would `psk2` (or another pattern) be better for a handshake where both sides know only a shared
   key?
2. Is `snow`'s stateless transport mode, with an explicit counter nonce and our own replay window, used safely?
   Are there misuse risks (nonce reuse across a restart, a session reused after rekeying) that the design misses?
3. Is HKDF-SHA256 with a fixed salt and info a sound way to turn the 160-bit password into the 32-byte psk? Should
   the protocol version be bound into the Noise prologue as well?
4. Are 160 bits of password, a 16-bit checksum and base32 text the right trade-off between safety and typing?
5. Are the amplification bounds (71-byte init, 59-byte response, no other replies) and the handshake limits (20 per
   second per IP, 64 half-open) enough, or should the server add a stateless cookie under load, as WireGuard does?
6. Is moving a session to a new address on any authenticated, fresh datagram (C8) safe, or should it wait for a
   few in a row?
7. Should keys and the password be wiped from memory after use (e.g. the `zeroize` crate)?
8. Is anything in section 7 worse than it looks?

## 10. Checklist for implementers

Before marking step C1 done, check each:

- [ ] No game message is ever sent or accepted outside a `Transport` datagram once a session exists.
- [ ] A counter is never reused under one key: one counter per direction per session, never reset, sessions never
      resumed after a restart.
- [ ] The replay window is updated only after a datagram authenticates.
- [ ] Nothing is allocated, and no reply is sent, for a datagram that doesn't authenticate (except `OtherVersion`
      and `HandshakeResponse` as specified).
- [ ] The password is never logged, printed, put on a command line, included in an error message, or drawn.
- [ ] Password files are written with mode 0600; reading a file with wider permissions warns.
- [ ] `warped-server` has no way to run without a password.
- [ ] The `snow` version is pinned, at least 7 days old, and its features are the default pure-Rust primitives.
- [ ] Every test listed in `authentication.md` exists, with its partition table, and passes.
- [ ] This document's evidence entries are changed from *planned* to the test names that provide them.
